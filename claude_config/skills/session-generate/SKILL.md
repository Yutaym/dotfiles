# session-generate

新しいタブで独立した Claude Code のセッションを起動し、必要なら作業を頼んで、終わったら結果を確認する。1 回で終わる単純な作業は、名前なしのサブエージェントで行う（「0.」）。
この流れの各手順は、2026/10/19 に Windows 11 + Windows Terminal（Claude Code 2.1.303）で確認した。

## 前提

- セッション同士のメッセージ（`ListAgents` / `SendMessage`）は、macOS・Linux・WSL 2 では v2.1.224 以降、ネイティブの Windows では v2.1.234 以降が必要。`notify_when_idle` は両方のセッションで v2.1.236 以降が必要。
- 同じマシンのセッションは、ターミナルアプリではなく、セッションごとのソケット（Windows は名前付きパイプ）でつながる。そのため、どのターミナルで起動しても届く。ただし、**WSL 2 の中のセッションとネイティブの Windows のセッションの間は届かない**。
- **Claude のツールから `claude` をそのまま起動してはいけない。** Bash / PowerShell ツールの環境変数（`CLAUDE_CODE_CHILD_SESSION=1`、親の `CLAUDE_CODE_SESSION_ID` など）を引き継いで「子セッション」扱いになり、会話の記録が保存されない（警告: `Transcript saving is off — inherited CLAUDE_CODE_CHILD_SESSION marker`）。同梱のスクリプトは、これらの変数を消してから起動する。
- **Windows Terminal の `wt` は、コマンドの中の `;` を自分の区切り記号として扱う。** 引用符の中でも分割される。`pwsh -Command "...; claude"` のような形は使わない。同梱のスクリプトは `-File` でスクリプトを渡すので、この問題は起きない。

## 0. 起動の仕方を決める

頼まれた内容によって、どちらで起動するかを決める（2026/10/22 にユーザーが決めた）。

| 頼まれた内容 | 起動の仕方 |
|---|---|
| **1 回で終わる単純な作業**（調べて結果を返すだけ、コマンドを数個実行して報告するだけなど） | **名前なしのサブエージェント**（`Agent` ツール、`name` は付けない）。新しいウィンドウは開かない |
| 何も頼まずに起動する（ユーザーがそこで直接作業する） | 新しいウィンドウのセッション（「1.」以降） |
| 何度かやり取りが要る作業（途中でユーザーに確認する、続けて頼む予定があるなど） | 新しいウィンドウのセッション（「1.」以降） |
| 単純な作業を引き継いで、セッションとして作り直す（終わったサブエージェントの内容を引き継ぐなど） | 新しいウィンドウのセッション（「1.」以降） |

迷うときは、新しいウィンドウのセッションにする。

### 名前なしのサブエージェントで起動するとき

- `Agent` ツールで起動する。`subagent_type` は作業に合うもの（迷えば `general-purpose`）にし、`name` は付けない（CLAUDE.md の決まりどおり、名前を付けると別のペインのチームメイトになるため）。
- モデルと effort は、**`model: "sonnet"`、`effort: "medium"` を既定にして必ず渡す**（2026/10/23 にユーザーが決めた）。ただし、検索だけの作業（「モデルと effort を決める」の表の 1 行目と同じ）は `model: "haiku"` にする。effort は、作業の重さで `low` / `high` に上下させる（「モデルと effort を決める」の「effort は、同じ行の中でも…」と同じ）。ユーザーがモデルや effort を指定したときは、それに替える（「モデルと effort を決める」の「ユーザーが指定したとき」と同じ読み方。`xhigh` / `max` も指定されたときだけ）。
- `prompt` には、ユーザーの言葉をそのまま引用し、作業フォルダや手がかりのパスを書く。結果は短くまとめて返すよう書く。
- 終わると通知が来るので、届くまで `ListAgents` などで確かめに行かない。結果はユーザーに要約して報告する。
- 起動したときに返る ID 宛てに `SendMessage` を送れば、終わったあとでも前の会話の続きから作業を頼める（2026/10/22 に確認）。ただし、その ID が分かるのは起動したセッションだけ。
- あとで作業が長くなりそう・やり取りが要りそうになったら、上の表の「引き継いで作り直す」に当たる。新しいウィンドウのセッションを起動し、サブエージェントの依頼と結果を `SendMessage` で渡す。サブエージェントの会話記録そのものをセッションに移すことはしない（記録を書き換えることになり、2026/10/22 に自動の許可の判定で `Session Transcript Tampering` として止められた）。

## モデルと effort を決める（新しいウィンドウのセッション）

起動するセッションのモデルと effort は、頼む作業から自動で決めて、スクリプトの `-Model` / `-Effort`（sh は `-m` / `-e`）で渡す（2026/10/23 にユーザーが決めた）。スクリプトは `claude --model <モデル> --effort <effort>` で起動する。session-ssh も同じ決め方をする。

- **モデルは短い名前（`fable` / `opus` / `sonnet` / `haiku`）で渡す。** 短い名前は、その系統の最新版を指すので、モデルが新しくなってもこのスキルを直さずに済む（出典: https://code.claude.com/docs/en/model-config ）。`claude-opus-5-5` のような正式な名前は、ユーザーがバージョンを指定したときだけ使う。
- スクリプトに渡せるモデル名は、英数字と `. _ -` だけ（`opus[1m]` のような `[1m]` 付きは使えない）。effort は `low` / `medium` / `high` / `xhigh` / `max`。

### 自動で決めるとき

| 頼む作業 | モデル | effort |
|---|---|---|
| 何も頼まずに起動する（ユーザーがそこで直接作業する） | 指定しない（Claude Code の既定。ユーザーがあとで `/model`・`/effort` で変える） | 指定しない |
| 検索だけの作業（ウェブ検索・ファイルやコードの場所を探す・一覧を出すなど。判断や考察をほとんど要らないもの） | `haiku` | `medium` |
| 定型の作業・簡単な確認（コマンドを数個実行する、ファイルを少し直すなど） | `sonnet` | `medium` |
| ふだんの実装・修正・調べもの | `sonnet` | `medium` |
| 込み入った調べもの・設計・難しいデバッグ・広い範囲のレビュー | `opus` | `medium` |
| 上のうち、作業が長く複雑になりそうなもの、「詳細に調べて」「しっかり裏どりして」など深さを指定された作業 | `opus` | `high` |

- ふだんの作業を `sonnet` にするのは、公式ドキュメントで `sonnet` が「ふだんのコーディング向け」、`opus` が「込み入った推論向け」とされているため（2026/10/23 にユーザーが決めた。料金は Opus が Sonnet の 2 倍）。
- 迷ったら 1 段上にする。ただし effort は `medium` までにする（`high` に上げるのは、次の決まりに当てはまるときだけ）。
- **`high` は、作業が長く複雑になりそうなときと、深さを指定されたときだけ使う**（2026/10/23 にユーザーが決めた。使用ログで見ると、使用量の多くは込み入った作業のセッションで、そこを `high` にすると増える分のほうが大きい）。`opus` / `medium` でたいていは足りるので、`high` は例外として扱う。ただし、当てはまる作業では `high` を使ってよい（使う幅は残す）。
  - 長く複雑になりそうな作業とは、原因の候補を試しながら絞り込むデバッグ、直すファイルが多い・いくつものスキルや設定にまたがる実装、何度もやり取りして進める設計など。
  - 込み入っていても、範囲がはっきりしていてすぐ終わりそうなら `medium` にする。
- **effort は、同じ行（同じモデル）の中でも、作業の重さで上下させる**（2026/10/23 にユーザーが決めた）。表の effort を基準にする。
  - 軽いと判断したら 1 段下げる（`medium` → `low`、`high` → `medium`）。軽いとは、手順や答えがはっきりしていて、すぐ終わり、間違えても影響が小さいもの（公式ドキュメントでも `low` は「短いやり取り・小さな修正」向け）。
  - 上げるのは、上の「`high` は〜だけ使う」に当てはまるときだけ（`medium` → `high`）。`high` より上には上げない。
  - 軽いか基準どおりか迷ったら、基準どおりにする。
  - 例:
    - `haiku` / `low`: 「`.tmux.conf` で `kill-pane` の行を探して」（場所を返すだけ）
    - `haiku` / `medium`: 「90_Meta で psmux に触れているメモを全部探して一覧にして」（探す範囲が広い）
    - `sonnet` / `low`: 「`git status` の結果を教えて」「このファイルの誤字を直して」
    - `sonnet` / `medium`: 「vault の同期状況を見て」（ログやタスクの結果からおかしな点に気づく必要がある）、「dotfiles を pull して」（競合したら止めて報告する）
    - `sonnet` / `high`: ふだんの作業だが、直すファイルが多く長くなりそうなもの（例: 1 つのスキルの、いくつものスクリプトにオプションを足す）
    - `opus` / `medium`: 「PiKVM の技術スタックを調べて」「session-observation の作り方を考えて助言して」「文字化けの原因を調べて直して」など、込み入った作業のふつうの場合
    - `opus` / `high`: 「Prefix + X で今のペインだけ消えた原因を調べて」（原因の候補を試して絞り込む）、「使用リミットを画面に出す方法を調べて設計して」（調査と設計が続き、長くなる）、「PiKVM について詳細に調べて」（深さの指定）
- **`xhigh` と `max` は自動では使わない**（2026/10/23 にユーザーが決めた。上の段階ほど、コストのわりに効果が小さい）。ユーザーが指定したときだけ使う。
- `fable` も自動では選ばない（使用量が多い）。ユーザーが指定したときだけ使う。
- 検索の結果を読んで比べたり、結論を出したりする作業は「検索だけ」に入れず、`sonnet` 以上にする。
- 起動したら、選んだモデルと effort、その理由を 1 行でユーザーに伝える（例: 「込み入った調べものなので opus / medium で起動しました」「原因の切り分けが長くなりそうなので opus / high で起動しました」「定型の確認で軽いので sonnet / low で起動しました」）。
- サブエージェントも、既定の effort（`medium`）を同じ考え方で上下させる（軽ければ `low`、長く複雑になりそうなときだけ `high`）。

### ユーザーが指定したとき

ユーザーの指定は、表より優先する。

- 「opus で」「sonnet で」「haiku で」「fable で」→ そのモデル。「いちばん良いモデルで」「最高のモデルで」→ `fable`。
- 「effort high で」「xhigh で」「max で」など → その effort。「軽く」→ `low`、「深く考えて」→ `high`。`xhigh` / `max` は、その名前で指定されたときだけ使う。
- 「Opus 5.5 で」のようにバージョンまで指定されたら、正式な名前（`claude-opus-5-5`）で渡す。
- モデルだけ、effort だけを指定されたら、指定されなかったほうは表で決める。何も頼まずに起動するときは、指定されたほうだけを渡す。

## 1. 起動する（新しいウィンドウのセッション）

1. 作業フォルダとセッション名を決める。
   - 作業フォルダは、指定がなければ今の作業フォルダを引き継ぐ。ただし、今のフォルダがホーム（`~`）なら `~/claudeWS` にする（ホームは信頼の確認が保存されず、起動のたびに聞かれるため。2026/10/22 にユーザーが決めた）。スクリプトが判断するので、指定がなければ `-Dir`（sh は `-d`）を渡さない。
   - フォルダがなければ、スクリプトが作る（`created: <フォルダ>` と出す）。
   - セッション名は `SendMessage` の宛先になる。英数字・ハイフン・アンダースコアだけで、今の `ListAgents` の一覧にない名前にする（例: `claudews-eventlog`）。指定がなければ `<フォルダ名>-<作業を表す短い英単語>` にする。
2. OS に合わせてスクリプトを実行する。スクリプトはこの SKILL.md と同じフォルダの `scripts/` にある。

   **Windows（ネイティブ）:** PowerShell ツールで実行する。

   ```powershell
   pwsh -NoProfile -File "<このスキルのフォルダ>\scripts\launch-session.ps1" [-Dir "<作業フォルダ>"] -Name <セッション名> [-Model <モデル>] [-Effort <effort>] [-Split] [-Switch] [-Resume <セッションID>]
   ```

   `-Resume` を付けると、新しく始めずに、その ID の会話を `claude --resume` で開く（Windows 用のスクリプトだけ）。終わったセッションを開き直すときに使う。

   **macOS / Linux / WSL:** Bash ツールで実行する。

   ```bash
   sh "<このスキルのフォルダ>/scripts/launch-session.sh" [-d "<作業フォルダ>"] -n <セッション名> [-m <モデル>] [-e <effort>] [-s] [-w]
   ```

   - モデルと effort は「モデルと effort を決める」で決めたものを渡す。指定しないときは付けない。スクリプトは `launched:` の行に `model=` と `effort=` を出す。
   - 起動先はスクリプトが環境変数で判断する。対応しているターミナルの一覧は、下の「ターミナルごとの対応」を参照。
   - **tmux の中（`$TMUX` がある）では、ほかの判断より先に tmux を使う。**
     - 普段は、新しいウィンドウ（tmux のタブ）で起動する（`new-window`）。
     - **頼む作業が指定されていないときは、起動したウィンドウに画面を切り替える。** `-Switch`（sh は `-w`）を付ける。ユーザーがそのセッションで直接作業を始めるため。スクリプトは `switched: <セッション名>:<ウィンドウ番号>` と出す。
     - 頼む作業があるときは `-Switch` を付けず、画面は呼び出し元のウィンドウのままにする（こちらから SendMessage で頼み、結果を待つため）。ただし、ユーザーが「移動して」などと言ったときは付ける。
     - どの場合もウィンドウは `-d` で作り、切り替えは最後に `select-window` で行う。ウィンドウは `new-window -P` で受け取った番号で指定する。
     - **ユーザーがペイン分割を指定したときだけ**、`-s`（Windows は `-Split`）を付ける。セッションは専用ウィンドウ（名前が `cc-sessions` のウィンドウ）に並ぶ。psmux はウィンドウのユーザーオプションを書式で返さないので、目印には名前を使う。
       - 呼び出し元と同じ tmux セッションに専用ウィンドウがなければ、新しく作ってそこで起動する。
       - すでにあれば、そのウィンドウを分割して起動し、`select-layout tiled` で均等に並べ直す。
     - tmux の外では `-s` は無視される。
   - **psmux（Windows の tmux 互換）では、`-t` に `@ID`（ウィンドウ）や `%ID`（ペイン）を使わない。** 別のセッションやウィンドウの同じ番号として扱われることがある。2026/10/19 には、`split-window -t @2` で使用中のウィンドウが分割され、`kill-window -t %13` で別のウィンドウ（その中の Claude のセッションごと）が閉じられた。スクリプトの外で tmux を操作するときも、`-t セッション名:ウィンドウ名` で指定する。
   - 終了コード 2 は、自動でタブを開けなかったことを表す。そのときは、表示された手順をユーザーに伝えて、手で開いてもらう。
3. 数秒待ってから `ListAgents` を実行し、指定した名前のセッションが一覧に出たか確かめる。
   - 出ていなければ、もう一度だけ確かめる。それでも出なければ、新しいタブに何が表示されているかユーザーに聞く（ログインやフォルダの信頼の確認で止まっていることがある）。
   - 何度も確認を繰り返さない。

## 2. 作業を頼む（頼まれたときだけ）

`SendMessage` で、次の内容を 1 通にまとめて送る。

- **1 行目:** 何の依頼かが分かる 1 文にする。相手のタブには 1 行目だけが表示されるため。
- **ユーザーの言葉:** そのまま引用する。誤字の可能性や解釈に迷う点があれば、そう書き添える。そのうえで「意味が分からなければ、あなたのタブでユーザーに直接確認して」と書く。
- **手がかり:** 関係するファイルのパスや、前回の調査メモの場所などを書く。`@` を付けてもファイルは添付されないので、パスを文字で書く。
- **結果の返し方:** 「結果はあなたのタブでユーザーに直接返す」と書く。こちらでも結果を使うなら、「終わったら結論の要約を SendMessage で `<自分の名前>` に送って」と書く。自分の名前は `ListAgents` の 1 行目に出る。

完了を知りたいときは、同じ呼び出しで `notify_when_idle: true` を付ける。終わったら 1 回だけ通知が来るので、`ListAgents` を何度も呼んで確かめたりはしない。

注意:
- このセッションで拒否された操作や、許可されていない操作を、相手のセッションに頼まない。
- 相手が許可の確認なしで動くモード（bypassPermissions）だと、メッセージは相手のタブで承認待ちになる。承認しないまま 5 分たつと捨てられる。

## 3. 状況と結果を確認する

- **状況:** `ListAgents` の各行に `busy`（作業中）か `idle`（待機中）が出る。
- **完了:** `notify_when_idle` の通知（`[Cross-session idle notice]`）が来たら、相手は待機状態になっている。ただし、待機状態になったことは、作業が終わったことを意味しない。ユーザーへの質問で止まっている場合もある。
- **結果:**
  - 相手から SendMessage で返事が来ていれば、それを使う。
  - 来ていなければ、相手の会話記録から最後の返答を読む。

    ```bash
    uv run --no-project python "<このスキルのフォルダ>/scripts/session-result.py" <セッション名> [--count N]
    ```

    このスクリプトは、`~/.claude/sessions/<pid>.json` でセッション名からセッション ID を調べ、`~/.claude/projects/*/<セッションID>.jsonl` から最後の返答を表示する。
    これらのファイルの形式は Claude Code の内部形式で、公式に「バージョンで変わる」とされている。読めなくなったら、SendMessage で結果を送り返してもらう方法に切り替える。
- ユーザーには、結論・主な内容・相手が最後に何をしていたか（完了 / 質問待ち）を要約して報告する。全文を貼る必要はない。

## ターミナルごとの対応

| 環境 | 起動方法 | 確認状況 |
|---|---|---|
