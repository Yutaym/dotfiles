# session-overview

同じマシンの Claude Code のセッションを一覧にし、会話記録を読んで、それぞれの状況を短く要約する。
相手のセッションにメッセージは送らない（相手の作業を止めず、相手のトークンも使わない）。

## 1. 生きているセッションを調べる

`ListAgents` を実行する。一覧に出たセッションが、今動いているセッションである。
- 生きているかどうかは、`ListAgents` に出るかで判断する。
- 状態（`busy` / `shell` = 作業中、`idle` = 待機中、`waiting` / `requires_action` = 返事待ち）は、「2.」のスクリプトの `状態:` の行（`sessions/*.json` の `status`）を正とする。session-observation の監視画面と同じ値にするため（2026/10/26 にユーザーが決めた）。`ListAgents` の値とずれていても、表には `状態:` の行の値を書く。
  - `状態:` の行がないとき（会話記録やファイルが読めないとき）だけ、`ListAgents` の値を書く。
  - このマシン以外のセッションが `offline` かどうかは、`ListAgents` で判断する（下の決まり）。
- `~/.claude/sessions/` には終了したセッションの情報が残っていることがあるので、生きているかどうかの判断には使わない。
- クラウドや別のマシンのセッション（`ListAgents` の行に `cloud` / `Remote Control` と出るもの）は、会話記録がこのマシンにない。Remote Control のセッションは、ssh で開いたウィンドウがあれば「2.」の `remote-overview.py` で相手のマシンの記録を読んで要約する。
  - **`remote-overview.py` で読めなかった Remote Control のセッションは、表に入れない。** 番号も振らない。中身が分からず、表が長くなるだけのため（2026/10/22 にユーザーの指示で外した）。
  - **クラウドのセッション（`cloud`）は、表に入れない。** 番号も振らない。会話記録が読めず、名前と状態しか分からないため（2026/10/22 にユーザーの指示で外した）。
  - **このマシン以外のセッションで、状態が `offline` のものは表に入れない。** 以前に Remote Control でつないだセッションが、終わったあとも一覧に残るため（2026/10/22 には 11 個残っていた）。番号も振らない。
  - このマシンのセッションは、状態にかかわらず表に入れる。
  - このセッションが Remote Control につながっていないときは、このマシン以外のセッションは `ListAgents` に出ない。
- 引数でセッション名が指定されたら、そのセッションだけを対象にする。

## 2. 会話記録から材料を抜き出す

このマシンのセッションの名前を並べて、スクリプトを実行する（スクリプトはこの SKILL.md と同じフォルダの `scripts/` にある）。

```bash
uv run --no-project python "<このスキルのフォルダ>/scripts/session-overview.py" <名前1> <名前2> ... [--prompts N] [--chars N]
```

スクリプトは、セッションごとに次の項目を表示する。
- 番号（No に使う）と sessionId
- 状態、フォルダ、起動の時刻、自動で付いたタイトル、最後に会話した時刻
- 依頼の最初と最後の N 件（既定は 2 件）。それぞれ、ユーザーが入力したものか、別のセッションから届いたもの（送り主の名前付き）かが分かる。
- 最後の返答

`--prompts` と `--chars` で、表示する量を増やせる。要約するのに材料が足りないときに使う。
`--json` を付けると、同じ材料と、プロセスが生きているか（`alive`）を JSON で出す（session-observation スキルが使う）。

会話記録と `sessions/*.json` は Claude Code の内部形式で、バージョンが上がると変わることがある。項目が取れないときは、スクリプトを直す。

### Remote Control のセッション（ssh で開いたウィンドウがあるとき）

表に入れる Remote Control のセッション（offline でないもの）があれば、その名前を並べて次も実行する。

```bash
uv run --no-project python "<このスキルのフォルダ>/scripts/remote-overview.py" <名前1> <名前2> ... [--prompts N] [--chars N]
```

- このマシンの tmux（psmux）で、ssh-generate / session-ssh スキルで開いたウィンドウ（ペインのオプション `@ssh_host` に接続先が入っている）を探し、その接続先ごとに ssh で session-overview.py を動かす。出力の形は session-overview.py と同じで、各セッションの前に `# 接続先: <Host> (ssh を開いているこのマシンのウィンドウ: 0:3 dotfiles-mac, 0:7 mac-test)`（番号とウィンドウ名） が付く。
- 接続先のマシンにも、このスキル（`~/.claude/skills/session-overview`）と uv が必要。ssh は `BatchMode=yes` で実行するので、パスワードを聞かれる接続先は読めない。
- 接続先のシェルは、sh 系（bash / zsh など）と、既定のシェルが PowerShell の Windows に対応する。接続先ごとに ssh で `$PSVersionTable.PSEdition` を出させて判断する。
  - 2026/10/22 に、Home_Desktop_PC_1_win の `pcwin-dotfiles` を読めることを確認した。最初は sh 系のコマンド（`exec "$SHELL" -lic ...`）だけを送っていたので、PowerShell で `exec` が見つからずに失敗し、表に出なかった。
- どの接続先でも見つからなかったセッション（ssh で開いていないマシンのもの、自動で付いた名前のものなど）は、表に入れない（「1.」を参照）。
- 2026/10/22 に、Home_Mac_1 で session-ssh スキルで起動したセッション（`mac-test`）を読めることを確認した。

## 3. 一覧にして報告する

次の表にまとめる。セッションの一覧は、対象が 1 つだけのときも含めて、**常にこの表の形で出す**（箇条書きや文章だけにしない）。

| No | セッション | 状態 | 場所 | 何をしているか | 最後の動き |
|---|---|---|---|---|---|

- **No:** セッション番号。スクリプトの `番号:` の行の値をそのまま書く（2026/10/22 から。session-kill・session-observation の監視画面と同じ番号にするため）。
  - 番号は `~/.claude/session-numbers.json` に記録され、セッションが終わるまで変わらない。新しいセッションには、空いている一番小さい番号が付く。表に入れないセッションにも番号は付くので、表の番号は飛ぶことがある。
  - このマシンのセッションは sessionId、ssh の接続先のセッションは「接続先|sessionId」で番号を振る（`remote-overview.py` がこのマシンの表で振る。接続先の session-overview.py は `--no-number` で動かし、接続先には番号を記録しない）。
  - `番号: -` のとき、または `番号:` の行がないとき（接続先の session-overview.py が古いなど）は `-` と書く。
  - 表の行は No の小さい順に並べる。このセッション自身は、番号を書いて最後の行に置く。
- **セッション:** tmux の中で開かれているセッション（`ListAgents` の行に `tmux ...` の位置が出るもの）は、名前を太字にする（例: `**claudews-psmux**`）。tmux の外のセッションは太字にしない。
- **状態:** スクリプトの `状態:` の行の値（「1.」を参照）の前に、色の絵文字を付けて書く（session-observation の監視画面の色に合わせる）。`idle` 以外（`busy`、`waiting` など）は値を太字にする。`idle` は太字にしない。
  - 🟢 `idle`（例: `🟢 idle`）
  - 🟡 `busy`・`shell`（例: `🟡 **busy**`、`🟡 **shell**`）。`shell` は、シェルのコマンドを動かしている間の作業中の状態（Claude Code の本体も `busy` と同じ「作業中」として出す。2026/10/26 に claude.exe 2.1.310 の中身で確認）
  - 🔴 `waiting`（返事待ち。例: `🔴 **waiting**`）
  - 🔴 `idle` で「最後の動き」が「返事待ち?」（推定）のとき: `🔴 idle（返事待ち?）`（太字にしない。監視画面でも、この idle は赤で出す）
  - 🟣 そのほかの値（例: `🟣 **offline**`）
- **場所:** フォルダと、どこで動いているかを書く（例: `claudeWS / tmux 0:8`、`claudeWS / terminal`、`dotfiles / その他（VS Code）`）。どこで動いているかは、スクリプトの `場所:` の行で分かる（claude の親プロセスから判断する）。
  - `tmux (0:8 claudews-tabkey)` → `tmux 0:8`（tmux のセッション 0・ウィンドウ番号 8）。`ListAgents` の `@ID` / `%ID` ではなく、この番号を書く（psmux では番号のほうが確実なため）。
  - `terminal (windowsterminal)` → `terminal`（tmux の外のターミナルのタブ）。
  - `other (code)` → `その他（VS Code）`。`code` 以外は、プロセス名をそのまま括弧に書く。
  - `不明` → `不明`。
  - `remote-overview.py` で読んだセッションは、接続先とこのマシンのウィンドウを書く（例: `Home_Mac_1:dotfiles / ssh 0:7`）。フォルダは接続先のパスの最後の名前にする。同じ接続先のウィンドウが複数あるときは、ウィンドウ名がセッション名と同じもの（session-ssh で開いたもの）があればそれだけを書き、なければ全部を書く。
- **何をしているか:** 依頼とタイトルから、1 行で書く。別のセッションから頼まれた作業なら、「〜から依頼」と書き添える。
- **最後の動き:** 最後に会話した時刻と、次のどれに当たるかを書く。
  - 先頭に絵文字を付ける（🟡 作業中 / 🟢 完了 / 🔴 返事待ち。記録なしは付けない）。
  - **🟡 作業中:** 「状態」が `busy` か `shell` のとき。
  - **🟢 完了:** 最後の返答が結果の報告になっているとき。結論を 1 行で添える。
  - **🔴 返事待ち:** 「状態」が `waiting` のとき（確か）。または、「状態」が `idle` で、最後の返答の終わりのほうにユーザーへの質問がある（推定）とき。推定のときは「返事待ち?」と `?` を付け、`waiting` の「返事待ち」と区別する（session-observation の監視画面と同じ。判断の基準は `session-overview.py` の `QUESTION_RE` / `judge_waiting`。`observe.py` はそれを呼ぶ）。
    - **返事待ちかどうかは、スクリプト（`session-overview.py`）の出力の `判定:` 行（`返事待ち` / `返事待ち?` / `なし`）に従う。** 自分で最後の返答を読み直して決めない（読み方がぶれて、session-observation の監視画面と食い違うため）。同じ関数（`judge_waiting`）を監視画面も使う。`--json` では `wait` の値。`判定:` 行がないとき（会話記録なし、接続先のスクリプトが古いなど）は、下の基準で判断する。
    - 質問とみなすのは、文末が `？` / `?` / 「ますか」「ですか」「でしょうか」のとき、または「教えて・選んで・決めて・知らせて・返信して・回答して・指示して」などに「ください」が付くとき。
    - 次は返事待ちにしない: 「実行したら言ってください」「確認してください」のような作業のお願い（返事が要らない。完了または次の手順として扱う）、「崩れていたら教えてください」のような条件付きの依頼。
    - 該当するのは、ユーザーへの質問や確認で終わっているとき。何を聞いているかを添える。「どれにしますか」などの質問のあとに、「※ 〜」の補足だけが付いて終わっている返答も、返事待ちとする（最後の一文だけで「完了」と決めない。末尾の「次の手順」のような節に、ユーザーへの質問がないかを見る）。
  - **記録なし:** 会話記録がないとき。起動した直後か、記録の保存がオフの子セッションである。
- このセッション自身には「（このセッション）」と付ける。短く書くか、表から外してもよい。
- 起動した日と最後に会話した日が大きく離れているセッションは、古い会話を開き直しただけで、そのあと何もしていないことが多い。そのときは、そう書く。

**表のセルは短くする。** 1 つのセルが長い（目安は全角 30 字を超える）と、ターミナルの幅に収まらずに表が崩れる（2026/10/22 に、「最後の動き」に長い説明を書いて崩れた）。「何をしているか」「最後の動き」は要点だけにし、補足（推測の断り書きなど）は表の下の箇条書きに回す。

表の下には、ユーザーが対応したほうがよいものだけを、短く箇条書きにする。
- **「最後の動き」が返事待ちのセッションは、必ず 1 つずつ書く。** セッション番号（と名前）と、何の返事を待っているかを書く。選択肢があるなら、その名前を挙げる。例: `- No 7（dotfiles-pane-visibility）: 修正案 A〜F のどれを入れるかを選んでほしい`
  - 返事待ちが 1 つもなければ、この項目は書かない。
  - 表の「最後の動き」には「返事待ち」と短く書くだけにし、質問の中身は箇条書きのほうに書く（表のセルを短く保つため）。
- そのほかに対応したほうがよいもの（エラーで止まっているセッションなど）があれば、同じ箇条書きに足す。同じセッションを二重に書かない。
- session-kill スキルはこの表を使うが、箇条書きは書かない（session-kill の SKILL.md の決まり）。

要約に書くのは、抜き出した依頼と返答に書いてあることだけにする。材料が足りず推測が混じるところは、「嘘をついているかもしれない」と明記する。

1 つのセッションをもっと詳しく知りたいと言われたら、そのセッションだけを `--prompts` と `--chars` を増やして実行し直す。session-generate スキルの `session-result.py` を使えば、最後の返答を全文で読める。
