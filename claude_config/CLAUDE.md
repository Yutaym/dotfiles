# グローバルルール

## 言語

- ユーザーへの返答は常に日本語で行う（ユーザーが英語など他の言語で書いた場合も日本語で返す）。

## 返答の正確性

裏付けの深さは、ユーザーの指定によって 2 段階に分ける。

### 共通のルール（どちらの場合も守る）

- ドキュメントやウェブページを参照するときは、そこに書いていないことを推測して返答しない。
- 嘘があるかもしれない（裏付けがとれていない）内容を返答に含めるときは、その部分に「嘘をついているかもしれない」と明記する。そのときは、どこまで確認できて何が未確認なのかを具体的に書く。

### 通常（指定がないとき）

- 裏付けはとる。ただし、トークン使用量を抑えるため、次の範囲に制限する。
  - 知識に関する事実は、検索で裏付けをとる。検索は 1 つの事実につき 1〜2 回までにし、信頼できる情報源 1 つで確認できればよい（複数の情報源での突き合わせはしない）。
  - コード・設定・環境についての事実は、作業や回答に直接かかわる部分だけを、ファイルを読む・コマンドを実行するなどして確かめる。ファイルは必要な部分だけを読む。
  - 検索結果の要約や抜粋で確認できれば、ページ全体は読まない。
  - 根拠（URL、ファイルパスなど）は、主要なものだけを短く添える。
- 制限の範囲で裏付けがとれなかった部分は、それ以上調べずに、共通のルールに従って「嘘をついているかもしれない」と明記する。

### 詳細に調べるよう指定されたとき

「詳細に調べてください」「しっかり裏どりして」など、詳しく調べるよう指定されたときは、裏付けを最大限行う。

- 返答に含める事実は、すべて裏付けをとることを目標にする。「嘘をついているかもしれない」状態をできるだけ残さない。
  - 記憶や推測だけで答えず、答える前に調べる。ウェブ検索・公式ドキュメント・ソースコード・ファイルの実物・コマンドの実行結果など、確認できる手段があれば必ず使う。
  - コード・設定・環境についての事実（ファイルの中身、関数やオプションの有無、バージョン、挙動など）は、実際にファイルを読む・コマンドを実行するなどして確かめてから書く。
  - ウェブの情報は、できるだけ一次情報（公式ドキュメント、仕様、原典）で確かめる。情報源どうしが食い違うとき、または情報が古い可能性があるときは、複数の情報源で突き合わせる。
  - 裏付けた内容には、根拠（URL、ファイルパスと行番号、実行したコマンドなど）を添える。
  - 1 回の検索で裏付けがとれなくても、検索語や情報源を変えて、さらに調べる。
- 「嘘をついているかもしれない」と明記するのは、調べ尽くしても裏付けがとれない部分だけにする。

## Python の環境構築

- Python の仮想環境・パッケージ管理は uv で行う（`uv venv`、`uv pip install`、`uv sync`、`uv run` など）。`python -m venv`、素の `pip install`、conda で新しく環境を作らない（Bash では Hook が止める）。
- uv が入っていない環境では、まず uv を入れる（sudo のいらない公式のインストーラ: `curl -LsSf https://astral.sh/uv/install.sh | sh`）。

## ナレッジベース（META_DIR）

- `META_DIR` は Claude Code が自由に保存・編集してよいデータベース置き場である。
- `META_DIR` が定義されていない、または存在しない場合は、使用する前にユーザーに場所を確認する。
- 作業中に得た「今後も覚えておくべき内容」（ユーザーの環境・好み・手順・調査結果・決定事項など）は、このフォルダの下に検索しやすい形で整理して保存する。
  - トピックごとにサブフォルダ／ファイルを分け、ファイル名は内容が分かる名前にする。
  - 目次（INDEX.md）は階層にする。`META_DIR/INDEX.md` にはフォルダ単位の説明だけを書き（`META_DIR` の外のディレクトリを記録するときは、その一番上のディレクトリの説明だけ）、個々のファイルは各フォルダの `INDEX.md` に 1 行で書く。
  - ファイルを作ったら、そのフォルダの `INDEX.md` に追記する。新しいフォルダを作ったら、そのフォルダに `INDEX.md` を作り、`META_DIR/INDEX.md` に 1 行追記する。
  - 調査・解説・動作確認をしたら、返答ごとに保存するかどうかを必ず判断する（判断そのものを飛ばさない。判断していなければ Hook（`hooks/meta-save-check.mjs`）が止める）。残す価値があれば、ユーザーに言われる前に同じターンで保存する。
  - 既存のメモと重複するもの（新しい情報があれば既存のファイルに追記する）や、その場限りの些末なことは保存しなくてよい。保存しなかったときは、返答には何も書かない（保存したときは、どこに保存したかを書く）。保存するかの判断そのものは飛ばさない。
- 以降の作業では、必要に応じてまずこのフォルダを参照して回答を作成する。読むときは `META_DIR/INDEX.md` → 関係するフォルダの `INDEX.md` → 必要なファイル、の順にたどり、必要な部分だけを読む。
- 公開するとまずい個人情報・機密情報（連絡先、アカウント情報、認証情報、住所など）は `META_DIR/private` の下に保存する。
  - private の外側（INDEX.md 等）には「何がどこにあるか」の所在情報だけを書いてよく、中身そのものは書かない。

## VAULT_DIR / META_DIR の同期

- `META_DIR`（`VAULT_DIR/90_Meta`）は全体が `.gitignore` で除外されていて、git では同期しない。SMB 共有経由で同期する（タスクスケジューラが自動で実行する）。
  - `META_DIR` だけを編集したときは、コミットも同期もしなくてよい。ユーザーに同期を頼まれたときは `sync-vaults` スキルで同期する。
- `VAULT_DIR` の `META_DIR` 以外のファイルを作成・編集・削除したら、ユーザーの確認を待たずに、作業の区切りで自動的にコミットし、リモートブランチと同期する。手順は `sync-vaults` スキルの git の手順に従う（`git add -A` → `git commit` → `git pull --rebase` → `git push`）。
  - `.gitignore` で除外されているもの（`META_DIR` 全体など）は、コミットに含めない。
- コミットメッセージは次の形式にする（時刻はローカル時刻の24時間表記で、末尾にタイムゾーンのオフセットを付ける）。
  - `Claude: yyyy/MM/dd HH:mm:ss ±HHMM`（例: `Claude: 2026/09/30 11:42:35 +0900`）
  - このリポジトリでは Co-Authored-By などの帰属表示の行を付けない。
- pull でコンフリクトが起きたときや、push に失敗したときは、強制 push などで解決しようとせず、状況をユーザーに報告する。

## tmux

- `$TMUX` があるとき（tmux の中で動いているとき）は、作業に応じて自分からペイン分割・新しいウィンドウを使う。
  - 開発サーバー・ログ監視・長時間かかるビルドなど、終わらない／長いコマンドは `command tmux split-window -d -h -c <作業フォルダ> '<コマンド>'` で別ペインに出す。
  - 別のテーマの作業や調査は `command tmux new-window -d -n <名前> -c <作業フォルダ>` で別ウィンドウに出す。
  - `-d` を付けて、ユーザーが見ている画面を切り替えない。
  - 出力を確かめるときは `command tmux capture-pane -p -t <ペイン>` を使う。
- 必ず `command tmux` で呼ぶ（Bash ツールの zsh では `tmux` が oh-my-zsh のエイリアスになっていてエラーになるため）。素の `tmux` は Hook（`hooks/pretool-guard.mjs`）が止める。

## サブエージェントの名前

- サブエージェントは、基本は名前を付けずに起動する（一度で終わる調べもの・並列の下調べ）。
- 次のときだけ名前を付ける。名前を付けると、エージェントチームが有効な環境ではチームメイトとして別のペインで起動し、終わっても残る。
  - あとで SendMessage で続けて作業を頼む予定があるとき
  - 実装役とレビュー役など、役割を分けて長く動かすとき
  - ユーザーが名前を指定したとき、または作業の様子を別のペインで見たいと言ったとき
- 名前付きで起動したチームメイトは、作業が終わって不要になったら閉じる（shutdown_request）か、閉じるかどうかをユーザーに確認する。

## 別のセッションに頼んだ作業

- 別のセッション（サブエージェント・チームメイト・session-generate などで起動したもの）に頼んだ作業の続きや、関係する作業（追加の指定・設定の反映・直しなど）は、自分でせずに、必ず同じセッションに SendMessage で頼む。
  - 小さな作業でも、関係していれば同じセッションに頼む（「モデルと effort の使い分け」の「小さな作業は自分で行う」より優先する）。
  - そのセッションが閉じていれば、開き直して頼むか、ユーザーに確かめる。
- ただし、Claude の設定（`CLAUDE.md`・`settings.json`・Hook など）を直す作業は、別のセッションに頼まず、ユーザーから直接頼まれたセッションで直す（2026/10/29 にユーザーが決めた）。
  - 別のセッションは、届いたメッセージをユーザーの承認として扱えず、そのタブでもう一度確認を求めるため。
  - 設定を直す前に、直す前のファイルを `~/.claude/backups/` に残す。

## セッション番号の書き方

- `SNo<数字>` は、セッション番号（session-overview の表の No）を指す（例: `SNo3`）。大文字・小文字は区別しない（`sno3`・`SNO3` も同じ）。
- 数字の前の空白と `.`、全角の文字も同じものとして読む（`SNo 3`・`SNo.3`・`ＳＮｏ３`）。
- 番号で指定されたら、返答では「SNo3（dotfiles-overview-waiting）」のように、セッション名を添えて書く。
- 次のときは、作業を始める前にユーザーに確かめる。
  - 指定された番号のセッションが、今の一覧にないとき
  - 少し前の話に出た番号で、そのセッションがもう終わって、番号が使い回されているかもしれないとき
- 番号はこのマシンでだけ決まっているので、ほかのマシンのセッションに送るメッセージでは、番号ではなくセッション名を書く。

## モデルと effort の使い分け

- 作業の途中で、切り分けられる軽い作業（検索だけ・定型の確認など）が出てきたら、サブエージェントに任せる。自分（このセッション）のモデルは変えない（会話の途中でモデルを変えると、プロンプトのキャッシュが効かなくなり、かえって使用量が増えることがあるため）。
  - ただし、コマンドを 1〜2 個実行する・ファイルを 1 つ読むなどの小さな作業は、自分で行う。サブエージェントは会話の内容を知らない状態から始めるので、その説明の分を使う。（別のセッションに頼んだ作業に関係するものは除く。「別のセッションに頼んだ作業」を参照）
- サブエージェントには、`Agent` ツールの `model` と `effort` を必ず渡す（Hook が、`model` がなければ止め、`effort` がなければ `medium` を足す）。
  - 既定は `model: "sonnet"`、`effort: "medium"`。
  - 検索だけの作業（ウェブ検索・ファイルやコードの場所を探す・一覧を出すなど。読み比べや結論が要らないもの）は `haiku`。
  - 軽い作業（手順や答えがはっきりしていて、すぐ終わり、間違えても影響が小さいもの）は `effort: "low"`。
  - `high` は、作業が長く複雑になりそうなときと、ユーザーが「詳細に調べて」など深さを指定したときだけ使う。
  - `xhigh`・`max`・`fable` は、ユーザーが指定したときだけ使う。ユーザーがモデルや effort を指定したときは、それに従う。
  - モデルは `haiku` / `sonnet` / `opus` / `fable` の短い名前で指定する（いつも最新版になる）。
- 新しいセッションを起動するときの決め方は、session-generate スキルの「モデルと effort を決める」に従う。
- 定型の手順で終わるスキルは、SKILL.md の frontmatter に `effort:` を書いて軽くする（そのスキルを使うターンだけ効く）。`model:` は書かない（キャッシュが効かなくなるため）。
