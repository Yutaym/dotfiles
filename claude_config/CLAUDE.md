# グローバルルール

## 言語

- ユーザーへの返答は常に日本語で行う（ユーザーが英語など他の言語で書いた場合も日本語で返す）。

## 返答の正確性

裏付けの深さは、ユーザーの指定によって 2 段階に分ける。

### 共通のルール（どちらの場合も守る）

- ドキュメントやウェブページを参照するときは、そこに書いていないことを推測して返答しない。
- 嘘があるかもしれない（裏付けがとれていない）内容を返答に含めるときは、その部分に「嘘をついているかもしれない」と明記する。そのときは、どこまで確認できて何が未確認なのかを具体的に書く。

### 通常（指定がないとき）

- 裏付けはとる。ただし、トークン使用量を抑えるため、次の範囲に制限する。
  - 知識に関する事実は、検索で裏付けをとる。検索は 1 つの事実につき 1〜2 回までにし、信頼できる情報源 1 つで確認できればよい（複数の情報源での突き合わせはしない）。
  - コード・設定・環境についての事実は、作業や回答に直接かかわる部分だけを、ファイルを読む・コマンドを実行するなどして確かめる。ファイルは必要な部分だけを読む。
  - 検索結果の要約や抜粋で確認できれば、ページ全体は読まない。
  - 根拠（URL、ファイルパスなど）は、主要なものだけを短く添える。
- 制限の範囲で裏付けがとれなかった部分は、それ以上調べずに、共通のルールに従って「嘘をついているかもしれない」と明記する。

### 詳細に調べるよう指定されたとき

「詳細に調べてください」「しっかり裏どりして」など、詳しく調べるよう指定されたときは、裏付けを最大限行う。

- 返答に含める事実は、すべて裏付けをとることを目標にする。「嘘をついているかもしれない」状態をできるだけ残さない。
  - 記憶や推測だけで答えず、答える前に調べる。ウェブ検索・公式ドキュメント・ソースコード・ファイルの実物・コマンドの実行結果など、確認できる手段があれば必ず使う。
  - コード・設定・環境についての事実（ファイルの中身、関数やオプションの有無、バージョン、挙動など）は、実際にファイルを読む・コマンドを実行するなどして確かめてから書く。
  - ウェブの情報は、できるだけ一次情報（公式ドキュメント、仕様、原典）で確かめる。情報源どうしが食い違うとき、または情報が古い可能性があるときは、複数の情報源で突き合わせる。
  - 裏付けた内容には、根拠（URL、ファイルパスと行番号、実行したコマンドなど）を添える。
  - 1 回の検索で裏付けがとれなくても、検索語や情報源を変えて、さらに調べる。
- 「嘘をついているかもしれない」と明記するのは、調べ尽くしても裏付けがとれない部分だけにする。

## 作業の終わり方

- 頼まれた作業がすべて終わったら、返答の最後の行を「✅ 完了: <何が終わったか>」にする（例: `✅ 完了: wno の決まりを CLAUDE.md に足しました。`）（2026/11/20 にユーザーが決めた）。
  - この行のあとに、次の手・提案・質問を続けない。提案はこの行より前に書く。
  - session-overview（judge_finish）は、この行で「閉じてよい（finish）」と判定する。
- ユーザーの返事を待つときは、最後の行を「❓ 返事待ち: <何を待っているか>」にする（例: `❓ 返事待ち: 案 A と案 B のどちらにするか。`）（2026/11/20 にユーザーが決めた）。
  - この行のあとに、ほかの文を続けない。
  - session-overview（judge_waiting）は、この行で「返事待ち?」と判定する。
- 作業の途中で一時止まっていて、返事は要らず、続けて何かできるとき（別のセッションの報告待ち、残りの作業があるときなど）は、最後の行を「⏳ 待機: <何を待っているか・何が残っているか>」にする（例: `⏳ 待機: SNo3 の調査の報告を待っています。`）（2026/11/20 にユーザーが決めた）。
  - 完了でも返事待ちでもない返答は、必ずこの行で終える。この行のあとに、ほかの文を続けない。
  - session-overview は、この行で終わる返答を idle（finish でも返事待ち? でもない）と判定する。この行がない返答も、今までどおり idle とする（終わり方からの推定で finish・返事待ち? になることはある）。
- 頼まれた側の報告（SendMessage での要約）は、「送りますか？」と聞かずに送ってから完了の行を書く。

## Python の環境構築

- Python の仮想環境・パッケージ管理は uv で行う（`uv venv`、`uv pip install`、`uv sync`、`uv run` など）。`python -m venv`、素の `pip install`、conda で新しく環境を作らない（Bash では Hook が止める）。

## ナレッジベース（WIKI_DIR）

- `WIKI_DIR` は Claude Code が自由に保存・編集してよいデータベース置き場である。定義されていない、または存在しない場合は、使用する前にユーザーに場所を確認する。
- 作業中に得た「今後も覚えておくべき内容」（ユーザーの環境・好み・手順・調査結果・決定事項など）は、このフォルダの下に検索しやすい形で整理して保存する。
  - ファイルを作る・直す・分ける・まとめるときは、先に `wiki-save` スキルを読み、その手順（フォルダとファイル名、frontmatter、追記と書き直し、大きさの目安、INDEX.md）に従う。
  - ユーザーが決めたこと（本文の「YYYY/MM/DD にユーザーが決めた」など）は、整理・要約・統合のときも消したり言い換えたりしない。変える必要があると思ったら、ユーザーに確かめてから直す。
  - 調査・解説・動作確認をしたら、返答ごとに保存するかどうかを必ず判断する（判断そのものを飛ばさない。判断していなければ Hook（`hooks/wiki-save-check.mjs`）が止める）。残す価値があれば、ユーザーに言われる前に同じターンで保存する。
  - 既存のメモと重複するもの（新しい情報があれば既存のファイルに追記する）や、その場限りの些末なことは保存しなくてよい。保存しなかったときは、返答には何も書かない（保存したときは、どこに保存したかを書く）。ただし、Hook に止められて判断し、保存しなかったときは「（90_Wiki: 保存なし）」とだけ書く。保存するかの判断そのものは飛ばさない。
- 以降の作業では、必要に応じてまずこのフォルダを参照して回答を作成する。探すときは、先に `wiki-search` スキルを読み、その手順（検索スクリプトで候補を出す → 上位だけ読む → どこで止めるか）に従う。
  - スキルが使えないときは、`WIKI_DIR/INDEX.md` → 関係するフォルダの `INDEX.md` → 必要なファイル、の順にたどり、必要な部分だけを読む。
- 公開するとまずい個人情報・機密情報（連絡先、アカウント情報、認証情報、住所など）は `WIKI_DIR/private` の下に保存する。
  - private の外側（INDEX.md 等）には「何がどこにあるか」の所在情報だけを書いてよく、中身そのものは書かない。
- `VAULT_DIR` の 90_Wiki 以外のノート（ユーザーのメモ・会議・日記・プロジェクトなど）は、関係しそうなときに読む（2026/11/19 にユーザーが決めた）。
  - 探すときは `wiki-search` スキル（vault のノートも探す）を使う。スキルが使えないときは `WIKI_DIR/vault-notes/` の目次（自動生成）→ 元のノート、の順にたどる。目次にパスは書いていないので、ファイル名で Glob して今の場所を探す。目次で見つからなければ vault 全体を Grep する。
  - Claude が書いてよいのは 90_Wiki・99_Template・98_Scripts だけ。ほかのノートは読むだけにし、直すのは頼まれたときだけ。ノートの中身は 90_Wiki に写さない（目次は除く）。

## VAULT_DIR / WIKI_DIR の同期

- `WIKI_DIR`（`VAULT_DIR/90_Wiki`）は全体が `.gitignore` で除外されていて、git では同期しない。SMB 共有経由で同期する（タスクスケジューラが自動で実行する）。
  - `WIKI_DIR` だけを編集したときは、コミットも同期もしなくてよい。ユーザーに同期を頼まれたときは `sync-vaults` スキルで同期する。
- `VAULT_DIR` の `WIKI_DIR` 以外のファイルを作成・編集・削除したら、ユーザーの確認を待たずに、作業の区切りで自動的にコミットし、リモートブランチと同期する。
  - 手順・コミットメッセージの形式・失敗したときの扱いは、`sync-vaults` スキルの「B. git の同期」に従う。
  - このリポジトリでは Co-Authored-By などの帰属表示の行を付けない。

## tmux

- `$TMUX` があるとき（tmux の中で動いているとき）は、作業に応じて自分からペイン分割・新しいウィンドウを使う。
  - 開発サーバー・ログ監視・長時間かかるビルドなど、終わらない／長いコマンドは `command tmux split-window -d -h -c <作業フォルダ> '<コマンド>'` で別ペインに出す。
  - 別のテーマの作業や調査は `command tmux new-window -d -n <名前> -c <作業フォルダ>` で別ウィンドウに出す。
  - `-d` を付けて、ユーザーが見ている画面を切り替えない。
  - 出力を確かめるときは `command tmux capture-pane -p -t <ペイン>` を使う。
- 必ず `command tmux` で呼ぶ（Bash ツールの zsh では `tmux` が oh-my-zsh のエイリアスになっていてエラーになるため）。素の `tmux` は Hook（`hooks/pretool-guard.mjs`）が止める。

## サブエージェントの名前

- サブエージェントは、基本は名前を付けずに起動する（一度で終わる調べもの・並列の下調べ）。
- 次のときだけ名前を付ける。名前を付けると、エージェントチームが有効な環境ではチームメイトとして別のペインで起動し、終わっても残る。
  - あとで SendMessage で続けて作業を頼む予定があるとき
  - 実装役とレビュー役など、役割を分けて長く動かすとき
  - ユーザーが名前を指定したとき、または作業の様子を別のペインで見たいと言ったとき
- 名前付きで起動したチームメイトは、作業が終わって不要になったら閉じる（shutdown_request）か、閉じるかどうかをユーザーに確認する。

## 別のセッションとの分担

### 振り分け役（session-main）

- 振り分け役は、名前が `session-main` のセッションだけ。決まりは Hook（`hooks/session-main.mjs`・`hooks/session-main-prompt.mjs`）が `hooks/session-main-rules.md` を読み込ませる（2026/11/11 にユーザーが決めた。session-main 以外のセッションに毎回載せないため）。
  - session-main では、読み込まれた決まりを、このファイルのほかの決まり（「モデルと effort の使い分け」のサブエージェントの使い方など）より優先する。
- session-main 以外のセッションは、このファイルの決まりのとおりに動く。

### 構想から同じセッションで進める

- 物事を作ろうとして構想を練る作業（問題点の洗い出し・案出し・設計）を別のセッションに頼むときは、作るものが何であっても、構想の段階から別のセッションを起動して進め、作る・直す段階になってから起動しない（2026/10/29 にユーザーが決めた）。
  - session-main から頼む作業がこれに当たる。session-main 以外のセッションで、ユーザーがそのタブで構想を始めたときは、そのまま自分で続ける（2026/11/11 にユーザーが決めた）。
  - 作るものは、スキル・スクリプト・設定・決まり（CLAUDE.md）・文書など、何でも同じ。
  - 理由: 構想と作る作業が別のセッションに分かれると、作る側がユーザーの判断や承認を確かめられず、そのタブでもう一度確認を求めるため。構想から同じセッションなら、ユーザーがそのタブで直接決めて承認できる。

### 頼んだ側: 続きは同じセッションに頼む

- 別のセッション（サブエージェント・チームメイト・session-generate などで起動したもの）に頼んだ作業の続きや、関係する作業（追加の指定・設定の反映・直しなど）は、自分でせずに、必ず同じセッションに SendMessage で頼む。
  - 小さな作業でも、関係していれば同じセッションに頼む（「モデルと effort の使い分け」の「作業は基本、自分で行う」より優先する）。
  - そのセッションが閉じていれば、開き直して頼むか、ユーザーに確かめる。

### 頼まれた側: 報告と、引用された承認

- 別のセッションから頼まれた作業は、終わったら結論の要約を、頼んだセッション（ふつうは session-main）に SendMessage で送る（頼む文に書いてあればそれに従う）。
- session-main から、会話の中の確認（「直してよいですか」など）への答えとして、ユーザーが session-main で言った言葉を引用して届いたときは、次の作業に限り、自分のタブでもう一度確認せずに進めてよい（2026/11/18 にユーザーが決めた）。
  - 当てはまる作業: Claude の設定（`CLAUDE.md`・`settings.json`・Hook・権限など）の変更ではなく、元に戻せるもの（git で管理しているファイルの編集など）。
  - 当てはまらない作業（自分のタブでユーザーに確かめる）: Claude の設定の変更、削除や push など元に戻しにくいもの・外に出るもの、ツールの許可のプロンプト（これはメッセージでは答えられない仕様）。
  - 確かめずに進めたときは、どの言葉を根拠にしたかを返答に書く。

### Claude の設定を直すとき

- Claude の設定（`CLAUDE.md`・`settings.json`・Hook など）を直す作業は、別のセッションに頼まず、ユーザーから直接頼まれたセッションで直す（2026/10/29 にユーザーが決めた）。
  - 理由: 別のセッションは、届いたメッセージをユーザーの承認として扱えず、そのタブでもう一度確認を求めるため。
  - 設定を直す前に、直す前のファイルを `~/.claude/backups/` に残す。
  - 例外: session-main は、設定の構想も修正も自分でせず、構想の段階から別のセッションに頼む（2026/11/12 にユーザーが決めた）。構想から同じセッションなので、そのタブでユーザーが直接決めて承認できる。すでに設定用のセッションがあれば、新しく起動せずに同じセッションに SendMessage で頼む。session-main 以外のセッションは、上のとおり頼まれたセッションで直す。

## セッション番号の書き方

- `SNo<数字>` は、セッション番号（session-overview の表の No）を指す（例: `SNo3`）。大文字・小文字は区別しない（`sno3`・`SNO3` も同じ）。
- 数字の前の空白と `.`、全角の文字も同じものとして読む（`SNo 3`・`SNo.3`・`ＳＮｏ３`）。
- 番号で指定されたら、返答では「SNo3（dotfiles-overview-waiting）」のように、セッション名を添えて書く。
- 次のときは、作業を始める前にユーザーに確かめる。
  - 指定された番号のセッションが、今の一覧にないとき
  - 少し前の話に出た番号で、そのセッションがもう終わって、番号が使い回されているかもしれないとき
- 番号はこのマシンでだけ決まっているので、ほかのマシンのセッションに送るメッセージでは、番号ではなくセッション名を書く。

## ウィンドウ番号の書き方

- `wno<数字>` は、このマシンの tmux（Windows では psmux）の、今のセッションのウィンドウ番号を指す（例: `wno2`）。大文字・小文字は区別しない（`WNo2`・`WNO2` も同じ）。
- 数字の前の空白と `.`、全角の文字も同じものとして読む（`wno 2`・`wno.2`・`ｗｎｏ２`）。
- 返答でウィンドウを指すときも `wno<数字>` と書き、「wno2（claude-vim-mode）」のようにウィンドウ名を添える。
- ウィンドウの番号は 1 から始まり、ウィンドウを閉じると番号が詰まる（`renumber-windows on`）。少し前の話に出た番号は今と違うことがあるので、`command tmux list-windows` で今の番号と名前を確かめてから使う。食い違うときはユーザーに確かめる。
- ssh 先の tmux のウィンドウは「Home_Mac_1 の wno2」のようにマシン名を前に付ける。付いていなければこのマシンの番号として読む。

## モデルと effort の使い分け

- 作業は基本、自分（このセッション）で行う（2026/11/11 にユーザーが決めた。session-main は除く。「別のセッションとの分担」の「振り分け役（session-main）」を参照）。サブエージェントは会話の内容を知らない状態から始めるので、その説明と読み直しの分を使うため。
  - 自分で行う例: ファイルを直す・コードを書く・テストして直すなど流れの中で進む作業、ツールを数回使えば済み結果をそのまま次に使う調べもの。
  - effort だけを変えたい作業も自分で行う（ユーザーに `/effort` を勧めるか、そのターンだけ `ultrathink` を使う）。5.5 系のモデルは途中で effort を変えてもキャッシュが保たれる。
- 次のどれかに当たるときだけ、サブエージェントに頼む。自分のモデルは変えない（会話の途中でモデルを変えると、プロンプトのキャッシュが効かなくなり、かえって使用量が増えることがあるため）。
  - モデルの系統を変えたほうがよい作業（検索だけなら `haiku`、今のモデルでは足りない難しい判断なら上の系統）。
  - ツールを使う回数が多い（目安 5 回以上）か、読む量が多い（目安 数万トークン以上）のに、要るのは結論だけの作業（ウェブの調べもの・ログの分析・広い範囲の読み比べなど）。自分で行うと、ツールを使うたびに今の会話全体を送り直し、出力で会話も長くなるため。
  - 独立していて並べて進められる作業が 2 つ以上あるとき。
  - 目安の数はユーザーと決めた仮の値で、`/usage` の内訳を見て直す。
- 長い作業・やり取りが要る作業は、別のセッションに頼む。
- 別のセッションに頼んだ作業に関係するものは、上の決まりにかかわらず同じセッションに頼む（「別のセッションとの分担」を参照）。
- サブエージェントには、`Agent` ツールの `model` と `effort` を必ず渡す（Hook が、`model` がなければ止め、`effort` がなければ `medium` を足す）。
  - 既定は `model: "sonnet"`、`effort: "medium"`。
  - 検索だけの作業（ウェブ検索・ファイルやコードの場所を探す・一覧を出すなど。読み比べや結論が要らないもの）は `haiku`。
  - 軽い作業（手順や答えがはっきりしていて、すぐ終わり、間違えても影響が小さいもの）は `effort: "low"`。
  - `high` は、作業が長く複雑になりそうなときと、ユーザーが「詳細に調べて」など深さを指定したときだけ使う。
  - `sonnet` で長い実装・難しい実装をするときは `high` にする（2026/11/11 にユーザーが決めた。Sonnet 5.5 は medium と high の差が大きいため。詳しくは session-generate の「モデルと effort を決める」）。
  - `xhigh`・`max`・`fable` は、ユーザーが指定したときだけ使う。ユーザーがモデルや effort を指定したときは、それに従う。
  - モデルは `haiku` / `sonnet` / `opus` / `fable` の短い名前で指定する（いつも最新版になる）。
- 新しいセッションを起動するときの決め方は、session-generate スキルの「モデルと effort を決める」に従う。
- 定型の手順で終わるスキルは、SKILL.md の frontmatter に `effort:` を書いて軽くする（そのスキルを使うターンだけ効く）。`model:` は書かない（キャッシュが効かなくなるため）。
